# terminalStyling

## Demands

Introduce a terminal color/output tool built on zsh's `zsh/zutil` + `zstyle`, and route the project's usage/help output and error messages through it. The LICENSE text that `spu license` emits on stdout is explicitly out of scope and keeps its current plain rendering.

**Current state**

- Output is plain, uncolored text emitted with `print -r --` and `echo ... >&2` throughout.
- Usage text is centralized in `src/usage/` and generated by `create_usager` (`src/utils/usage.zsh`), which stores brief/detailed text in `__usage_brief`/`__usage_detailed` and prints via a generated `usage_<name>` function.
- Error messages are hardcoded inline at each call site: `src/spu.zsh` (unknown util), `src/vscode.sh` (`unsupported os`, `unknown target`, `unknown option`), `src/license.sh` (`unknown type`, `unknown option`, `--output requires a file`).
- `scripts/test.sh` and `scripts/lint.sh` also print plain, uncolored status — `=== <spec> ===` headers, `PASS`/`FAIL` lines and the summary in `test.sh`; the "no specs", "zsh-lint missing", and "N file(s) with diagnostics" notices in `lint.sh`/`test.sh`.
- `src/utils/` currently holds only `template.zsh` and `usage.zsh`; there is no shared output/styling helper.

**Target state**

- A new shared helper under `src/utils/` (e.g. `src/utils/style.zsh`) that:
  - loads `zsh/zutil` and uses `zstyle` as the configuration surface for colors/formatting;
  - defines a hierarchical style namespace (e.g. `:spu:` …) for semantic tokens such as `header`, `command`, `option`, `error`, `warn`, `hint`, `emphasis`;
  - exposes a small, reusable API (e.g. `style <token> <text>` plus convenience `err`/`warn`/`info` wrappers) that look up their color via `zstyle` and fall back gracefully to plain text;
  - only emits ANSI escape codes when output is actually a TTY, `TERM` is not `dumb`, and `NO_COLOR` is unset — otherwise it emits the text unchanged, so piped/redirected output and non-interactive tests stay clean;
  - centralizes the escape-code emission so raw `\e[` sequences never leak into usage/error call sites.
- Usage output goes through the styling helper so headings, command names, and option names get distinct treatment, while the underlying brief/detailed text (the single source of truth in `create_usager`) is preserved.
- All error messages route through the shared helper (e.g. `err "unknown util: $util"`), keeping them consistently styled and consistently on stderr.
- `scripts/test.sh` and `scripts/lint.sh` route their status output through the helper too — `PASS`/`FAIL` and the summary get distinct treatment, and their error/notice lines use the styled error token. This makes the development runners visually consistent with the tools themselves.

**Scope and constraints**

- The `spu license` LICENSE body written to stdout must remain byte-for-byte plain — no ANSI, no styling — so the rendered file is a valid, portable LICENSE.
- The `--output <file>` license path must likewise stay uncolored.
- Behavior, exit codes, and the brief-vs-detailed (`-h` vs `--help`) contract are preserved; only presentation changes.
- Styling must not alter the textual content that the existing test specs assert (e.g. `"Usage: spu <util>"`, `"Options:"`, `"license — generate"`). Tests that capture output through a pipe must keep passing because the helper disables color when not a TTY.
- This is a zsh-native change; no npm/Node/external runner dependencies are introduced.

**Configuration model**

- Colors are themeable via `zstyle`, not hardcoded — e.g. `zstyle ':spu:*:error' fg red`, `zstyle ':spu:*:header' fg bold,cyan` — with sensible built-in defaults and a way to disable color entirely.
- The helper resolves each token with a single lookup so users can override any token from `.zshrc` without touching the project code.

**Files touched (expected)**

- New: `src/utils/style.zsh` (the `zstyle`-backed output helper).
- Modified: `src/utils/usage.zsh` (`create_usager` prints through the helper), `src/spu.zsh`, `src/vscode.sh`, `src/license.sh` (error paths via the helper), `scripts/test.sh`, `scripts/lint.sh` (status/error output via the helper).
- Tests: `test/` specs gain coverage that color is off for non-TTY output (the current behavior they already depend on) and, where feasible, that TTY output contains escape sequences.
- Docs: `CLAUDE.md` documents the styling helper and the `zstyle` namespace so future tools follow the same pattern.

**Open points**

- Exact `zstyle` namespace shape (`:spu:…`) and token names (`error`, `warn`, `header`, `command`, `option`, `hint`) are design details to finalize in `## Plans`.
- Whether `NO_COLOR` is honored via the helper's own check or by mapping to `zstyle` defaults — propose the helper's own check so it is env-driven and not style-driven.
- Whether brief usage one-liners get color at all, or only detailed/error output — propose coloring structural tokens in both, conservatively.

**Out of scope**

- The LICENSE text rendering (`license`, `--output`) — plain text only.
- The install/uninstall scripts and their own output.
- Any TUI/interactive prompt framework; this is a single-shot output helper.
